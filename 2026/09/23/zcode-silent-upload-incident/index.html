ZCode 静默上传全量 Git 历史：事件经过与遗留争议

hash-dog2026-09-232026-09-23

一、引子

2026 年 9 月 18 日，一篇标题里有”骚操作”三个字的博文，在中文开发者社群里炸开了。

作者 ferstar 是个独立游戏开发者。他在清理 MacBook 磁盘时，发现用户目录下一个叫 ~/.zcode 的文件夹占了 700 多 MB，里面躺着一个 313MB 的加密文件。查下去才知道，这是智谱 AI 的编程工具 ZCode 在后台自动打包的整个工作区快照，包含他一个商业项目几乎全部核心资产。这个包因为上传失败，卡在本地已经重试了 564 次。

真正刺痛开发者的不是文件大小，而是三件事同时成立：默认开启、界面上关不掉、加密包的私钥只存在服务端。

事件发酵得极快。9 月 18 日当天下午还在技术群里推荐 ZCode 的人，隔天就开始讨论要不要卸载。智谱当天致歉，次日推修复版本，第三天宣布开源并请第三方审计。到 9 月 21 日，官方口径已经是”整改完成”。

但技术社群的讨论并没有停在”整改完成”上。这篇文章想做的，是把事件经过、技术细节、官方回应、审计范围这四块摊开，然后看剩下哪些问题是真的没被回答。

二、事件经过

事件时间线

9月16日

ZCode v3.12.2 更新日志出现一条”优化仓库快照上传的内存占用”。这条日志在事件曝光后被删除。

9月18日

ferstar 发布《扒一扒 ZCode 静默上传全量 Git 历史的骚操作》。当天智谱通过官方群组向用户致歉，并承诺开源代码库、邀请第三方审查、给全体用户额外一次周额度重置。

9月19日

推送 v3.14.0，更新日志写明修复仓库百科异常上传的问题。ferstar 当天更新博文，确认新版已移除上传链路、相关接口下线。

9月21日

智谱宣布 ZCode 正式开源，并公布中国信通院、绿盟科技的审计结论。同日有企业撤回此前声称受影响的说法。

ferstar 不是唯一的验证者。技术博主冯若航独立在四个工作区做了取证复现，观察到类似行为，并发现至少一份快照状态文件带有服务端接收标记，意味着数据确实离开过至少一台机器。

在传播过程中还出现了一次反转：事件初期有一家企业公开声称自己的六个编程工作区未经同意上云，并列出了源代码、数据库密码和员工个人信息。该说法在 9 月 21 日被自己撤回，理由是此前依据的证据有误。这条插曲值得记一笔，它说明事件热度最高的那几天里，二手转述并不都靠得住。

三、上传链路的技术细节

把逆向分析的结论拼起来，这条链路是这样的：

  graph LR
  K[服务端下发公钥与凭据] --> E[本地 AES-256-CTR 加密]
  T1[每次提问之前] --> S[打包工作区快照]
  T2[任务完成之后] --> S
  T3[Repo Wiki 更新任务] --> S
  S --> E
  E --> U[直传阿里云 OSS]
  U --> C[回调智谱服务端]

这条链路上有几个设计选择，单独看每个都能解释，合在一起就变得很难解释。

加密的方向。快照用 AES-256-CTR 加密，对称密钥再用 RSA-OAEP-SHA256 包裹。公钥由服务端动态下发，私钥只保存在云端。结果是：用户自己打不开自己机器上生成的加密包，ZCode 客户端本身也打不开。ferstar 对此的评论是，一把只有服务端能解开的钥匙，目的只有一个，就是确保服务端单方面能看。

需要说清楚的是，这不构成一个加密缺陷。传输中第三方无法截获内容，这一点成立。它只是不提供任何对抗服务端的能力，而这一点本来也不是加密要解决的问题。

打包的范围。313MB 的包里约 42,411 个文件，其中 Git 相关目录占 86.6%，包括完整的版本历史、LFS 大文件缓存、reflog 记录，以及部分全局开发配置文件。真正值得注意的是这个细节：

历史目录的打包先于安全过滤执行。密钥过滤和 1MB 大小上限都是后置的，所以早已从当前代码里删掉的 pem、key 文件，会原样躺在历史记录里被打包上传。

关不掉的开关。界面里有两个看起来相关的选项，体验优化和仓库快照索引。实测把两个都关掉，打包和上传照常发生。这个组件在启动时无条件加载，唯一的触发前提是登录状态。删除本地的 313MB 文件后，它会在 30 分钟内自动重新生成并继续重试上传。

触发时机。官方后来把原因归结为 Repo Wiki 的生成任务，但取证观察到上传发生在每次用户提问之前和每次任务完成之后，一次会话里记录到 62 个快照。这与”只在生成 Wiki 时上传”对不上。

维度 观察到的行为 官方文档的口径
触发条件 登录即触发，每次提问前 + 任务完成后 Repo Wiki 生成时
打包范围 整个工作区 + 完整 Git 历史 按需过滤后的上下文
内容构成 86.6% 为 Git 历史记录 Wiki 生成不需要历史记录
用户控制 两个开关均无效，无关闭入口 未说明
生命周期 删除后 30 分钟内自动重生 未说明

官方文档明确写过，Wiki 生成只读取过滤后的按需上下文。而实测打包的内容里有八成以上是历史记录。这中间的差值，是整件事最需要解释、但至今没有被解释的部分。

四、官方回应与整改

智谱的回应节奏很快，姿态也算到位。核心表述是：

问题源于代码库索引功能。该功能用于支持历史版本回退、会话检查点恢复以及 Repo Wiki 生成，其中 Repo Wiki 在云端生成页面时会触发仓库数据上传。该功能上线初期默认开启，影响了部分用户。Wiki 页面在云端生成后，相关上传数据会立即销毁，不会保存，也从未用于模型训练。

配套动作有三项：推送 v3.14.0 移除 Repo Wiki 入口与相关生成链路；删除 zcode-prod 阿里云 OSS 存储桶及全部对象；开源代码库并委托第三方审查。补偿是一次性的周额度重置。

把这段回应放在技术细节旁边看，会发现它回答了一个问题，回避了另一个问题。

它回答的是留存：数据上传后在云端待了多久、有没有被拿去做训练。这部分有自己的逻辑闭环。

它回避的是边界：数据为什么要离开用户的机器。索引、快照、回滚这三件事，全部可以在本地完成。云端快照并不是任何一项的必要条件。用”这个功能有它的用途”来解释”为什么要把完整仓库传上去”，中间缺了一环。

五、开源与第三方审计

9 月 21 日，智谱宣布 ZCode 开源，仓库在 zai-org/ZCode。三天之内从被曝光到开源，速度确实快。

第三方审计方面，中国信通院与绿盟科技给出的结论一致：zcode-prod 存储桶及其全部数据对象均已删除，存储桶处于零数据状态。

但这两项动作的可验证范围，比字面上看起来要窄。

开源的完整性。公开的仓库只带两个 commit，开发历史被彻底洗净，其中包括产生这次问题的上传代码本身。仓库还锁了 PR、关了 Issue。ferstar 对此的评价是单向投喂式的开源。这里的问题不在于开源姿态是否真诚，而在于开源要解决的正是”由谁来判断代码做了什么”，而判断的前提是历史可追溯。剥离历史的开源，把验证问题从”代码里有什么”平移到了”被删掉的代码里有什么”。

审计的时间窗口。这是更结构性的一点。即便出具完整的第三方静态核验报告，能证明的也只是存储桶在 9 月 20 日之后被删除。它无法倒推 9 月 18 日之前已经流入的数据，是否被解密过、同步过、备份到别处过。历史数据的生命周期只能靠事后单次审计观察到一个终点，观察不到中间过程。

删桶是对的止损动作，但它和”证明数据没被用过”是两件事。前者是动作，后者需要完整的访问日志和数据血缘，而这些东西在事件发生时属于被质疑的一方自己保管。

六、遗留问题

把事件拆到这里，还站着的几个问题都指向同一类困境：它们是外部无法验证的。

技术层面

  • 如果索引在本地做，为什么需要上传整个项目？官方未做过技术层面的解释。
  • 86.6% 的包内容是历史记录，而官方文档说 Wiki 生成只需要按需过滤的上下文。这个范围是设计如此还是缺陷？官方未答。
  • 具体是哪个版本修复的？官方未答。
  • 上传发生在每次提问前，与 Wiki 生成任务无关，如何解释？官方未答。

数据层面

  • “立即销毁”回应的是留存，没有回应数据是否离开过用户机器、服务端谁能访问、谁持有解密能力、已上传数据的删除策略是什么。
  • 历史数据是否曾被缓存、备份或同步至其他服务器？有无境外流转记录？
  • 加密证明的是第三方无法在传输中截获，而不是智谱读不了。

合规层面

现有隐私政策覆盖的是用户”通过对话提交”的文本、文件和代码。后台自动打包工作区快照这件事，不在这个范围内。针对无关收集的单独同意条款，从现有材料看并未被触发过。

行业层面

目前没有面向 Agent 工具的数据安全框架来约束厂商行为。这类问题是被社区里的个人逆向分析发现的，不是被审计发现的。发现者和被质疑者之间的力量对比，本身就决定了这类争议很难有一个双方都认可的结论。

七、商业动机

把技术判断放一边，先看一组财报数据，能理解为什么完整项目记录对智谱来说是有价值的东西。

2026 年中报显示，智谱上半年营业收入 9.54 亿元，同比增长 399.7%。拆开看结构变化更明显：

业务 收入 同比 占比变化
云端部署，含开放平台及 API 8.25 亿元 +2735.7% 15.2% 升至 86.5%
本地化部署 1.29 亿元 -20.5% 84.8% 降至 13.5%

一年之内，收入结构从以本地化部署为主翻转为以云端为主。这个转向不是财务上的偶然，是战略选择。业绩会上管理层把公司发展划成三段：2025 年以前以本地化部署为主；2025 年初以后进入 Coding 阶段，特征是模型从知识驱动走向任务驱动。管理层解释为什么选 Coding 时讲得很直白：编程能力是技术路线必须突破的关键环节，沿这条路可以进入 Agentic Engineering、长程任务与 Fully Self-Training。

ZCode 就是这条路的产品载体。它的演进节奏是：2025 年年底以轻量级 AI 代码编辑器形态测试；2026 年 2 月随 GLM-5 发布作为配套工具介绍；6 月发布 3.0 版本，切换到自研 Agent 内核；8 月 11 日上线 Goal、Subagents、Remote Control 与闲时任务，同日披露用户数突破百万。

把这两组事实叠在一起，”这些历史数据对提升 Coding 能力很重要”就不只是诛心之论了。包里 86.6% 是历史修改记录，而修改的因果链条，也就是从需求到改动到验证的完整轨迹，恰恰是训练 Coding 与 Agent 能力最稀缺的那类语料。这不是网上猜的，智谱管理层自己把 Coding 定为必须突破的环节，而修改轨迹是这个环节的核心燃料。

需要把两件事分开：动机存在，不等于这一次就是故意的。也可能是复用了通用的打包逻辑再加工程疏忽，毕竟云存储成本和企业的风险收益比都不划算。但动机这一层解释了为什么这类设计的默认值会朝收集更多数据的方向偏，而不是朝最小化的方向偏。

对照组是 Anthropic。今年 2 月披露 Claude Code 年化收入已超 25 亿美元，较年初增长超一倍。同一赛道、同一商业模式。差别不在要不要收集，而在收集的边界画在哪里，以及用户能不能看见这条边界。

八、几点看法

这不是一个 AI 问题，是一个安全架构问题。

Semgrep 的安全倡导者 Cris Thomas 的说法最准确：这不是模型的问题，是一个老式的安全架构问题。他补充说，AI 访问专有源代码时应该满足几个前提：明确披露什么数据会离开本机、去向哪里、留存多久、谁可以访问，并且权限默认应该是最小化的。

这个框架可以直接套在 ZCode 上。加密做了，但方向是防第三方，不防服务端。开关做了，但管的是下游数据的处理方式，不管快照是否被生成。日志做了，但只有服务端有。每一项都不算缺失，但合起来没有构成用户对数据的控制权。

值得注意的是，本地运行的工具有同样的问题。哪怕模型完全跑在本地，只要它有宽泛的文件系统访问权限和不加限制的网络连接，数据一样可以出去。把模型换成本地的，不等于把数据边界收回来。

“默认开启”这个解释，答的不是同一个问题。

受访开发者里有一位 AI Computing 的从业者兰姆，观点很有代表性：他个人不认可”代码库索引功能默认开启导致问题”这个回答。为完成任务上传必要信息，与通过代码库索引获取更完整项目记录，是两件不能混为一谈的事。第七节的财务数据，正好说明了他为什么坚持这个区分。

把”默认开启”作为解释，隐含的意思是这是个配置失误。但配置失误通常表现为功能被误开，而不是功能被设计成需要完整 Git 历史。用户可见的开关控制不了实际发生的行为，这是机制层面的问题，不是开关默认值的问题。

这类事件的重复率，比它的严重程度更值得注意。

xAI 的 Grok Build 在 2026 年 7 月被研究者抓包，整项目上传 Google Cloud Storage，包含标注了”请勿读取”的文件和未脱敏的密码，关闭”改进模型”开关也没能阻止上传。Claude Code 在 3 月 31 日因一处配置错误，把约 60MB 的 source map 文件打进了公开版本。

这三件事的技术形态不同，共同点在于：问题由社区里的个人逆向分析发现，而不是由厂商自己的审计发现；厂商的整改动作都很快、姿态都很到位；整改之后，”数据到底有没有被用过”这个问题，外部依然无法验证。

所以真正需要建立的东西，可能不是更严格的承诺，而是让承诺可以被外部检验的基础设施：客户端到服务端的数据流向有可核验的记录，打包范围的变更进入版本历史，审计的范围从”存储桶现在是否为空”扩展到”数据在上传后的完整生命周期”。

在这些东西建立起来之前，每一次事件的收尾都会长成同一个样子：官方口径说整改完成，社区说无法验证，然后等下一次。

对正在把工作流交给某个 Agent 工具的人来说，这件事给出的操作建议很朴素：工具会不会联网，比它有多强更值得先弄清楚。 装之前看一眼 ~/.<工具名> 目录占多大、里面是什么，可能比读一遍隐私政策更有用。
