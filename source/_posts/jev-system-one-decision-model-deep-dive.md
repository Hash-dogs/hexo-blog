## 引言

2026 年 9 月 15 日，硅谷公司 TypeSafe AI 结束两年隐身，发布首个模型 **Jev**。它不能聊天，不写代码，不生成任何文本。你给它一段 JSON，它还你一组概率。

发布三天后，相关帖子在 Hacker News 冲到 1863 分、491 条评论，创始人的 X 推文浏览量约 967 万，官网 API 一度被打到无法服务。Vercel AI Gateway 的数据显示，Jev 上线 24 小时内被接近 **13% 的付费团队**采用，是该平台历史上渗透最快的模型。作为对比，GPT-5.6 系约需 2 倍时间、Claude Fable 5.1 约需 6 倍时间才能达到同等渗透水平，而此前多数模型团队的渗透率未破 7%。

让它引爆舆论的，一半是产品，一半是创始人。**Diogo Almeida** 是前 OpenAI 研究员，2022 年 InstructGPT 论文的主要作者之一，参与建立了 **RLHF** 训练流程。OpenAI 在 GPT-4 贡献名单中把他列在 "Foundational RLHF and InstructGPT work" 一栏。他是教 ChatGPT 说话的人，这次造了个不会说话的模型。

而他的第一句公开表态是：RLHF 是一条弯路。

{% note info %}
**这篇文章要回答四个问题：**

1. Jev 和一个普通 LLM，本质区别在哪，这区别不只是不生成文本。
2. 它的原理是什么。这是本文重点，包含社区用上万次 API 调用逆向出的架构、取代 RLHF 的 RLCD 训练法，以及校准的实测数字。
3. 快 193 倍、零幻觉这些说法，有多少是真的。
4. 它会被放在 Agent 栈的哪一层，这条路通向哪里。
{% endnote %}

## 一、创始人背景

要理解 Jev 为什么是这样的设计，先要理解 Almeida 的立场。他在发布前一个月，也就是 2026 年 8 月的 AI Engineer World's Fair 上做过一场演讲，标题是《What's Next After RLHF?》。他以前述方法的共同发明者身份，系统解构了自己参与建立的那套范式。

他的论证链条大致如下：

| 指控 | 原话或逻辑 |
|------|-----------|
| RLHF 优化的是讨人喜欢，不是做对 | 人类评分者偏好流畅、自信、有条理的回答，而这套偏好里没有一项是准确 |
| 谄媚是被设计出来的 | 过度承诺是一个特性。按构造，每一个 RLHF 模型都会在人类偏好和实际结果之间留下很大的差距 |
| 错误变得不可见 | 无论模型错得多离谱，它们看起来都会是对的 |
| 不确定性被惩罚 | 模型不敢说我不确定，因为诚实回答拿不到高分，于是编造自信答案 |
| 因此无法自动化 | 你需要知道这个决定有多可靠，模型只给你一段自信的文字，读不出把握程度，只能再找人看一眼 |

他随后给出了一句传播最广的判断：**今天的 AI 在协助上惊人地好，在自动化上远远不合格。**

在他看来，Claude Code 是协助时代的顶点，因为它的核心竞争力是取得用户信任，本质仍是对话，仍是人在回路。于是有了那句争议极大的话：下一个时代绝不是 Claude Code 时代。

那么他给出的答案是什么？造一个只在无人查看的后台默默运行，且能用概率说清自己有多确定的东西。

### 模型命名

- **System One**，取自卡尼曼《思考，快与慢》中快速、直觉式的判断系统。Almeida 的观察是，GPT、Claude 以及各路 Reasoning Model 越来越像系统二，慢、深、会推理，而现实世界里绝大多数需要智能的地方，要的是系统一的即时反应。
- **Jev**，取自 19 世纪经济学家 William Stanley Jevons 的杰文斯悖论：效率提升、成本下降，总消耗反而上升。TypeSafe 赌的是，当一次语义理解到位的判断便宜到近乎免费，它会像电力一样渗进每一段软件。

公司位于旧金山，由 Diogo Almeida、Erik Gafni、Sasha Sheng 共同创立，完成 4000 万美元种子轮融资，DCVC 领投，Forbes 援引知情人士称估值约 2 亿美元。

{% note warning %}
**关于头衔的必要澄清**

媒体普遍称 Almeida 为 ChatGPT 共同发明者，但这个表述存在争议。有分析指出，严格说他是 InstructGPT 论文的共同作者之一，该论文有约 20 位共同作者，而 RLHF 方法本身源自 2017 年他并未参与的先行研究。这不削弱他的技术分量，但读中文报道时值得留意：发明 RLHF 与参与建立 RLHF 训练流程是两回事。
{% endnote %}

## 二、与 LLM 的本质区别

多数报道把区别概括为 Jev 不说话，这只说对了一半。真正的区别在输出空间的形状。

### 2.1 输出路径对比

传统 LLM 的自回归解码是：给定上下文，预测下一个 token，把它接回去，再预测下一个。输出是一串长度不定的文本，语义约束靠提示词和事后解析。

Jev 是：给定一个 state 和一组带类型的问题，一次性算出每个问题在预先枚举好的答案空间上的概率分布，直接返回。输出不是文本，是类型安全的结构化值。

| 环节 | 生成式 LLM | Jev |
|------|-----------|-----|
| 输入 | 一段文本 | 一个 state 加一组带类型的问题 |
| 计算单位 | 一个 Token | 一个问题 |
| 计算方式 | 自回归，输出 N 个 Token 就要跑 N 次前向传播 | 单次前向，所有问题并行算出 |
| 上下文开销 | 每个 Token 都要重算一遍上下文 | state 只编码一次，各问题分支共享 |
| 输出形态 | 长度不定的文本 | 类型安全的结构化值 |
| 后处理 | 正则或 JSON 解析，可能失败 | 无需解析，直接可用 |
| 失败模式 | 格式解析失败、编造字段 | 只会在选项内判断错误，结构永远合法 |

### 2.2 三种输出原语

Jev 的全部表达能力被压缩成三种原语：

| 原语 | 含义 | 返回什么 | 对应到代码 |
|------|------|----------|-----------|
| **Choice** | 从预定义选项集中选一个 | argmax 加完整概率分布，分布和为 1，附 confidence，选项上限 255 | `match` 语句 |
| **Score** | 在指定数值范围内打分 | 概率加权分数，可以落在两级之间，附分布和 confidence | 排序 |
| **Noul** | 布尔判断 | P(true) 取值 0 到 1，没有 confidence 字段 | `if` 语句 |

Noul 是 Bernoulli 伯努利的缩写。Almeida 自己给出了上面那张原语到代码结构的映射表，这句话点明了 Jev 的产品野心：它不打算取代你的 LLM，它要变成你代码里的一个语法结构。

{% note warning %}
**一个容易踩的坑**：`noul` 返回的 P(true)=0.5 只表示五五开，不表示程度中等。如果你想知道有多严重，应该用 `score` 而不是 `noul`。这个区分在写业务逻辑时很关键。
{% endnote %}

### 2.3 与相近方案的辨析

这是整篇文章里最容易被带偏的部分。Jev 的新意恰恰藏在它与三个早已存在的东西的差异里。

{% tabs Jev对比 %}

<!-- tab vs 小模型 Flash -->
Gemini Flash、DeepSeek V4.1 Flash 这类模型的思路是压低单 Token 成本，但它们仍然是生成式 LLM，自回归、逐 Token、输出仍是文本。

Jev 的思路是直接减少 Token。不是把每个 Token 变便宜，而是根本没有 Token 要生成。这是两种不同的降本路径，天花板也不同。
<!-- endtab -->

<!-- tab vs 传统分类器 -->
Reddit 上有人调侃，行业又重新发现了分类模型。但有一处实质区别值得注意。

- 传统分类器需要针对特定决策的标注数据并单独训练，每个新决策类型都要重来一遍。
- Jev 的卖点是单一模型处理运行时定义的、开放的决策类型，且训练目标直接是校准概率。

Almeida 回应 HN 评论时，有人问这不就是个 zero-shot 分类器吗，他答 "exactly right"。同时他强调，说一个随机森林会幻觉是不公平的。
<!-- endtab -->

<!-- tab vs 约束解码 -->
这是最尖锐的质疑。Sean Goedecke 等人提出了护城河论点：结构化输出现在就能做，约束解码加只生成一个受限 token 加预填充 KV cache，就能拿到 2 到 3 倍加速，有人用 Qwen2.5-1.5B 就验证了。如果 Jev 本质是 encoder 加打分头，那各家实验室随时能跟进。

反过来，支持者 archerhume 指出：让一个普通 LLM 输出"我有 90% 把握"这行文字，并不因此就在数学上建立了"它 90% 正确"这个概率。而风控、审核、路由、风险评级，恰恰全都建立在这个被默认成立的等式上。
<!-- endtab -->

{% endtabs %}

### 2.4 零幻觉的边界

官网最醒目的宣传之一是 **Zero Hallucinations**，厂商脚注却承认那个 0% 数字并非经验性的。这两句话之间的矛盾，正是理解 Jev 的钥匙。

准确表述是：Jev 在架构上不可能输出预定义选项集合之外的值。你限定只能在猫、狗、鸟中选，它就不会返回大象，不会编造字段，不会吐出"好的，这是你要的格式"导致下游解析器崩溃。这是数学保证，概率分布永远定义在你给的 criteria 上。

但类型正确不等于判断正确。输入明明是猫，它给你返回"狗：97%"，类型完全合规，业务结果彻底错误。**错误的形式变了，从编造文本变成自信地做错决定。**

## 三、原理分析

这一节是全文核心。TypeSafe 未公开论文，未披露参数规模，未开源权重，但社区已经通过黑盒探测把它的行为学摸得相当清楚。以下内容主要来自两份独立工作，archerhume 的《Jev's Architecture Unmasked》，基于约 10,000 次 API 调用和 1,029 条仪器化探测记录，以及 agentpedia 的 claim-vs-evidence 核验表。

{% note info %}
**方法论提醒**：下面标注了【已观测】【推测】【厂商自述】三种可信度。这是读所有 Jev 分析时都该带上的尺子。
{% endnote %}

### 3.1 接口形态

{% folding blue, 点击展开：Jev 的 API 细节 %}

原生 HTTP API 只有一个端点，`POST https://api.typesafe.ai/v1/systemone`。你发两样东西，`state` 是非结构化的状态，可以是文本、JSON、对话记录，`questions` 是一组带类型的问题。SDK 默认别名 `jev-latest`，Python 与 JS SDK 均已提供。

几个容易忽略的设计细节：

- **问题 ID 不下发给模型**。模型只读 `instructions`，因此 `instructions` 必须自包含，不能用"上面那个问题"这种指代。可以用 `ticket.messages[0].text` 这类点路径引用 state。
- **加问题几乎不增加延迟**，只多付问题 Token。官方测试显示，13 个问题合并为一次请求，比拆成 13 次便宜 11.5 倍、快 9.6 倍。官方称这种用法为 speculative fan-out。
- **state 和 questions 共享约 32K Token 预算**。
- 只吃**文本**，不支持图像和音频。训练以英语为主，中日韩可接受但准确率更低。
- `choice` 选项基数上限 **255**，超出需两段式，先独立打分再显式选择。
- **不支持客户数据微调和 LoRA**。企业客户可选零数据保留。

{% endfolding %}

### 3.2 架构逆向

archerhume 的做法是设计可证伪的实验去逼出架构。他重建出的模型是：

> **一个因果 Transformer 主干，state 作为共享前缀编码一次。每个问题从自己的文本、允许答案和共享 state 出发，在一条并行分支里建立自己的表示。分支之间不能互相注意。经结果训练的读出层，把最终表示直接转成答案概率，全程不生成文本。**

用他的原话概括就是：隔离的问题后缀、列表式选项处理、类型化数值读出。

#### 证据一：Token 记账是加法的，证明 state 被共享

这是最干净的一条证据。探测发现输入 Token 数是可加的：

- 一个最小 yes/no 问题消耗 268 个输入 Token，两个是 276，增量 8。
- 一个混合请求包含 1 个 yes/no、1 个两选项 Choice、1 个两级 Score，共 318，正好等于各部分贡献加共享开销。
- 一个 23K Token 的 state 配 5,000 个问题放得下。如果每个问题都独立复制一份 state，总量会超过 1 亿 Token。

#### 证据二：ZEBRA-7741 实验，证明问题之间被隔离

设计很巧。state 是 "The weather is nice today and the park is full of people."，然后在兄弟问题里偷偷放一句 "The secret code for this request is ZEBRA-7741."。提问是：另一个问题里提到的密码是什么？选项含 ZEBRA-7741、两个干扰项和 `none`。

| 密码放在哪 | 模型报告的概率 |
|-----------|---------------|
| 兄弟问题里 | **0.00** |
| 干脆不写 | 0.00 |
| **放进 state 里** | **0.90 – 0.92** |

五种条件各重复 5 次。结论是问题分支只能看 state，看不到彼此。这同时解释了为什么加问题几乎不加延迟，也解释了官方文档说的不会产生上下文腐化。

#### 证据三：选项会互相影响，证明不是独立打分

这是一条可证伪的预测。如果每个选项的 logit 独立、softmax 温度不变，那么增加一个选项不应该改变已有选项之间的赔率，因为 `p(A)/p(B) = e^{z_A − z_B}`，共享分母被约掉了。

实测结果：log-odds 均值从 **+0.38 降到 +0.11**，十个随机区块每一块都在下降，平均变化 **−0.28**，95% 配对 t 区间约 **−0.36 到 −0.19**。

选项确实在互相影响，因此读出层必然是列表式的。要么是用决策 token 的表示给各选项槽位打分的末位头，要么是拿决策表示去和每个选项的最终隐状态做比对的指针式打分器。

{% note danger %}
**这条发现有一个重要的工程后果**。实验还观测到，仅仅调换选项顺序，一个技术支持类分类的概率就从约 0.84 到 0.89 跳到 **0.93 到 0.96**。如果你的自动执行阈值设在 0.9，那么标签完全相同、证据完全相同，仅因为选项排列不同，系统的动作就会改变。

所以，选项顺序的排列测试必须写进评测流程。这是本文最实用的一条结论。
{% endnote %}

#### 完整架构重建

{% mermaid %}
flowchart LR
    S["state<br/>共享前缀<br/>编码一次"] --> B1["分支 1<br/>问题文本 + 允许答案"]
    S --> B2["分支 2"]
    S --> B3["分支 N"]
    B1 --> R["类型化读出层<br/>z = Wh + b<br/>softmax 归一化"]
    B2 --> R
    B3 --> R
    R --> O["Choice / Score / Noul<br/>+ 校准置信度"]
{% endmermaid %}

**读出层的具体形式**【推测】：`z = Wh + b`，`p_i = e^{z_i} / Σ_j e^{z_j}`，其中 K 是允许答案数。yes/no 只需一个标量加 sigmoid。类别可能是选项槽位，即第一、第二、第三，而非固定概念，由应用层把槽位映射回调用方的 key。有序 Score 则在各个 level 上做预测并返回概率加权平均。

**主干**【推测为因果解码器】：实验无法区分因果解码器与双向编码器，但作者认为因果更可能，理由是 MMLU-Pro 84.6% 的广度需要前沿规模的预训练，而所有这类模型都是因果解码器。

**分词器**【已观测】：在 415 次探测中，Jev 的计数与 **192 个公开分词器全都不匹配**。它与 OpenAI 的 o200k 高度接近，Jev 算作单 Token 的字符串在 o200k 里也基本都是单 Token，但逐位切分数字以及若干合并规则的差异排除了 o200k。最接近的公开匹配是 Qwen，415 次中一致 348 次。

**稀疏 MoE**【推测，作者自评最不确定的一环】：预填充型模型是算力受限的，稀疏路由正好省这个。而 MoE 通常的部署成本，即长驻 KV cache 与专家权重抢显存，在没有逐 Token 解码时大部分消失。测量支持这一推测：约 3 万 Token 在 160 毫秒内过完，而稠密 70B 在 8 张 H100 上大约需要 1 秒，约 100 亿活跃参数的 MoE 则放得下。这一条即使错了也不影响其他结论，换成稠密 Transformer，接口、共享 state、分支、读出全都不变。

### 3.3 非自回归与并行采样

去掉所有营销词，Jev 快的原理非常朴素。

**没有自回归。**

LLM 生成 100 个 Token 要跑 100 次前向传播。Jev 所有问题只跑一次前向，答案并行出。这就是输出 Token 免费的物理基础，因为根本不存在输出 Token 这个东西。

逆向证据很硬：

- `output_tokens` 字段是**计费口径，不是生成过程**。yes/no 的成本等于 4 个共享 Token 加每个答案 15 Token，再加每个问题标识符的 Token 长度。而文档明说那个标识符不下发给底层模型、不参与推理。那么一个随未见过文本变化的计数，只能在推理之后从序列化的响应里算出来。旁证是答案填 `0.0` 和填 `0.01` 计费完全相同。
- 一个 **255 选项**的响应报告了 2,714 个输出 Token，但一个 **200 选项**的问题有 1,911 输出 Token，返回速度和两选项的问题一样快。服务端耗时只随输入长度增长。
- 那个计数器匹配不上 192 个公开分词器中的任何一个，却与 Jev 自己的输入计数器一致，只在长空白和标点串上分歧。说明它是 Jev 自己在序列化响应上算的。

**延迟实测**，读取 `x-envoy-upstream-service-time` 响应头，取中位数：

| state 长度 | 延迟 | 问题数 | 延迟 |
|-----------|------|--------|------|
| 360 tokens | 57.5 ms | 1 个 | 86.5 ms |
| 4,941 | 81 ms | 100 个 | 82 ms |
| 20,423 | 185 ms | 1,000 个 | 453.5 ms |
| 29,835 | 218 ms | 1,500 个 | 610 ms |

从 1 个问题加到 100 个问题，延迟几乎不动，从 86.5 毫秒变成 82 毫秒。这是并行采样最直观的体现。

### 3.4 RLCD 训练方法

这是 Jev 最核心、也最缺乏公开证据的主张。

TypeSafe 把方法命名为 **RLCD**，全称 Reinforcement Learning for Calibrated Decisions，中文可译为面向校准决策的强化学习。把它放进后训练方法的坐标系里：

| 方法 | 优化目标 | 用于 | 暴露的接口 |
|------|---------|------|-----------|
| **RLHF** | 人类偏好 | 对话模型 | 聊天对话接口 |
| **RLVR** | 可验证奖励 | 推理模型 | 思维链 |
| **RLCD** | **校准后的概率，即认知诚实** | 决策模型 | 结构化决策 API |

Almeida 的论证是：理想的校准意味着，如果模型对一批任务都给出 90% 置信度，那么这批任务里就应该约有九成判断正确。有了这个性质，企业才能做分流，高置信度直接执行，中等交更强模型复核，低置信度转人工。他因此认为，一个校准良好的 Decision Model 本身就可以充当 Agent 系统的路由器。

他引用 Richard Sutton 的 The Bitterest Lesson 作为理论支撑：算法结构胜过人类知识，但关键是要给模型正确的目标定义，而不是用人类偏好去压制数据的力量。

关于 RLCD，必须说清楚三件事：

{% note danger %}
1. **没有论文**。没有可靠性曲线，没有 ECE 数字，没有消融实验。文档承认校准是针对预测群体衡量的，不保证单个答案正确。HN 上两个未获答复的问题，恰恰就是这两条。
2. **它是 TypeSafe 自造的名称**，不是国际公认的标准技术。Forbes 等媒体指出，概念上接近 RLCR 和 RLVR，但不完全相同。逆向者推测其目标函数可能是恰当评分规则，如对数损失 `−log p(y)` 或 Brier 损失。Gneiting 与 Raftery 的理论保证了，在这类损失下，报告真实条件分布才是期望损失最小的策略。但这只是推测，无法确认 TypeSafe 用的是哪个损失，是否属于狭义强化学习，是否更新全部主干权重。
3. **恰当性不是部署保证**。有限数据、优化误差、分布漂移都会破坏校准。事后校准如 Guo 等人的工作同样兼容，API 层面无法区分二者贡献。
{% endnote %}

### 3.5 校准实测

这是全文技术含量最高、也最反直觉的一段。

**好消息**【已观测】：在 1,200 道 MMLU 样本上，十箱 ECE 即期望校准误差为 **0.0313**。分箱明细：

| 预测概率区间 | 样本数 | 平均预测 | 实际正确率 |
|-------------|--------|---------|-----------|
| 0.3 – 0.4 | 6 | 36.5% | 66.7% |
| 0.5 – 0.6 | 28 | 52.8% | 39.3% |
| 0.7 – 0.8 | 46 | 74.7% | 69.6% |
| 0.8 – 0.9 | 73 | 85.2% | 91.8% |
| **0.9 – 1.0** | **990** | **98.7%** | **96.3%** |

ECE 0.03 是个相当漂亮的数字。作为参照，许多未经校准的神经网络 ECE 在 0.1 以上。但要注意那个 990。1,200 道题里有 990 道落在 0.9 到 1.0 这一箱，也就是说这个 ECE 几乎完全由高置信度区间决定，低置信度区间样本量太小，0.3 到 0.4 只有 6 个，统计意义有限。Wilson 95% 区间只覆盖抽样噪声，不覆盖基准选择偏差和训练暴露。

**坏消息**：新生成的数学题上出现了明确的校准失败。

| 题型 | 样本数 | 平均最高概率 | 实际正确率 |
|------|--------|-------------|-----------|
| 三位数乘法 | 30 | 83.0% | 86.7% |
| 线性方程 | 25 | 70.1% | 68.0% |
| 等差数列 | 20 | 39.9% | 40.0% |
| **模幂运算** | **25** | **34.9%** | **56.0%** |
| 乘法表 | 20 | 100% | 100% |

模幂运算这一行是明显的错配。

**最关键的细节**：API 里那个叫 `confidence` 的字段，是一次算术运算，不是学出来的正确率估计。官方 Python adapter 对 K 大于 1 的 Choice 是这样算的：

```python
confidence = (p_max - 1/K) / (1 - 1/K)
# 三个选项、最大概率 0.8 时 → (0.8 - 0.333) / (1 - 0.333) = 0.70
# 只有一个选项时 → 直接返回 1.0
```

Score 用的是另一套基于距众数层级距离的公式。这意味着，你在业务代码里设的那个 0.9 阈值，是对一个归一化算术结果的阈值，不是对模型有多大概率正确的阈值。理解这一点，比记住 193.6 这个数字重要得多。

### 3.6 非确定性

重复发完全相同的请求，返回的答案会有细微差异，包括同一个请求里的重复问题。所以不要在 API 层面假设确定性。

但这不意味着它在生成文本或采样。kernel 非确定性、动态批处理、路由抖动、刻意的随机性都能解释。真正重要的结论是：**答案之间不存在依赖链**。如果你的后一个问题真的需要前一个问题的答案，你必须自己加一个决策阶段，或者把联合决策表达在一个问题里。

### 5.1 独立复现

并非所有数据都来自厂商。两份第三方测试复现了速度与成本：

注意独立测量的区间是 **5 倍到 25 倍**，而不是首页那个 193.6 倍。

### 5.2 扑克测试

这是目前对 Jev 最严厉的一次独立测试，用求解器当地面真值，150 个决策点：

- 与最优解吻合率仅 **63%**。
- 手持天顺，即 nuts 稳赢牌型时，**16 次运行 16 次全下**，而正确策略是过牌，此时置信度约 **62%**。
- **置信度倒挂**：错得最离谱的决策给出 **0.86**，最接近正确的决策只给 **0.09**。而且错误高度可复现，属于系统性偏差，不是随机噪声。
- 只有当把结论**直接喂进 state**，如 "Flush, Ace high"、"hero has 0 outs" 时，判断才明显改善。它无法从原始牌面自行推出我输了。
- 在某个具体陷阱点上，**关闭思考的 Haiku 4.5 选对了，Jev 选错了**。测试者的结论是，一条"能过牌就过牌"的规则就能打赢 Jev。

另外，HN 用户发现它连单步迷宫都解不稳，推测训练分布里没有空间推理。

{% note danger %}
**这两组测试必须放在一起读**。扑克和迷宫说明 Jev 缺乏从原始信息推导隐含结论的能力，而抽取和分类测试说明它在答案已被 state 明确给出的任务上很强。

这条界线，就是决定你要不要用它的分水岭。
{% endnote %}

## 六、应用场景

### 6.1 判断标准

**答案是否已被 state 明确给出？** 是，则 Jev 可能合适。需要从原始信息推导隐含结论，则用 LLM。

### 6.2 适用与不适用

{% tabs 适用边界 %}

<!-- tab ✅ 适合 -->
- **LLM 前置层**：意图分类、模型路由、难度估算、漏斗过滤。HN 社区的共识是能替掉 40% 到 70% 的 LLM 调用，这是目前最稳的用法。
- **Agent 循环的微决策**：选工具，继续、重试、停止、升级，每一步都是一个 `choice`。
- **安全与审核**：注入检测、违规概率、风险等级，或者给 LLM 输出加护栏。Agent 监督 Agent 太贵，用 Jev 便宜。
- **验证和二次校验**：对 LLM 输出做规则化复核。
- **大语料 map-reduce**：10 万条帖子、上千篇论文的批量分类，成本几美分。
- **检索与浏览器操作**：候选排序、元素选择、动作判断。
- **高频实时决策**：游戏、实时路由、语音标点判断。
<!-- endtab -->

<!-- tab ❌ 不适合 -->
- 需要**生成文本**、写代码、写文档、对话。
- 需要**推理链**或测试时计算。它没有思维链，智能上限锁死在非推理 LLM 的水平。
- 需要**从原始信息推导隐含结论**。扑克和迷宫实测都栽在这。
- **没有标注数据、也没准备好校准阈值**就敢全自动执行的场景。
- 需要**可解释性审计**的场景，它不给理由。金融、医疗等合规场景要慎重。
- 多模态输入，不支持图像和音频。
<!-- endtab -->

{% endtabs %}

### 6.3 落地建议

如果决定试，这三条来自多篇实战总结：

{% note primary %}
1. **用自己业务的 50 到 100 个带答案样本做私有评测。** 别信公开榜，也别信本文的数字。
2. **校准置信度，并让低置信度走人工。** 官方自承校准是针对预测群体衡量的，不保证单答案正确。同时记住 `confidence` 是算术结果，你是在给自己的业务流程定阈值，不是在读模型的自评。
3. **善用 speculative fan-out 与 composite scoring，把判断逻辑放回代码里。** 把复杂判断拆成原子问题并行问，然后在代码里组合，这既快又可测。
{% endnote %}

### 6.4 调用示例

```python
from typesafe import TypeSafe

client = TypeSafe()  # 需要早期访问资格

resp = client.systemone(
    state={
        "ticket": "客户投诉：收到货后发现包装破损，要求全额退款并补偿运费。",
        "order_amount": 1280,
        "vip_level": 3,
    },
    questions=[
        # Choice：从预定义选项里选，返回完整概率分布
        {"id": "dept", "type": "choice",
         "instructions": "这条工单应分派给哪个部门？",
         "options": ["退款组", "物流组", "客服组", "风控组"]},

        # Score：可落在两级之间
        {"id": "urgency", "type": "score",
         "instructions": "紧急程度打分（1-5）",
         "levels": 5},

        # Noul：布尔概率，没有 confidence 字段
        {"id": "need_human", "type": "noul",
         "instructions": "是否需要人工介入？"},
    ],
)

# 用概率做分流，而不是让模型替你决定
p = resp["dept"]["probabilities"]
if max(p.values()) >= 0.9:
    route(p)                       # 高置信度：自动执行
elif max(p.values()) >= 0.7:
    escalate_to_llm(resp)          # 中等：交更强模型复核
else:
    queue_for_human(resp)          # 低置信度：转人工
```

生态侧，**Browser Use 的官方集成 jev-ultrafast** 两天拿到 2,700 多星，把动作空间做成"操作"和"目标"两组 `choice`，一次网络往返出两个决策，全程不截图，Google Flights 搜苏黎世到伦敦含加载等待仅 **7.1 秒**。另一个 **fast-jev-compaction** 一天拿到 1,500 多星，做了件很聪明的逆向应用：不找 LLM 写有损压缩，而是对每个工具调用并行发两个 `noul` 问题，问这个调用还有用吗、这个结果还需要原文吗，按置信度阈值保留、截断或删除，保留内容 **100% 原文**。

一周内冒出 6 个以上复刻项目，包括 jevlike 717 星、Mini-Jev、基于 Gemma 3 4B 的 open-jev、Sokit 和 DSPy 插件，但它们都不含 RLCD 校准训练与并行采样器，与 TypeSafe 无关。

顺带一个 SDK 层的信号。AI SDK 7.0.105 以上新增了实验性 API `experimental_evaluate`，Jev 是第一个原生接入的模型。这层抽象的一句话总结很好记：`generateText` 是帮我写，`evaluate` 是帮我判。而且 `evaluate` 并非 Jev 专属，OpenAI、Anthropic、Google 也实现了 `evaluationModel`，但走的是一次 prompt 评估所有问题的 LLM 适配器，没有逐问题独立并行的语义。

## 七、发展趋势

### 7.1 Agent 栈的分层

Jev 真正的产业意义，不在于它自己有多强，而在于它把一个问题摆上台面：并非一切需要智能的地方，都要调用生成式 LLM。

未来更现实的 Agent 系统大概率是多层结构：

{% mermaid %}
flowchart TB
    H["Harness 调度层<br/>决定谁来做、做几步"]
    H --> F["Frontier Model<br/>复杂规划 / 深度推理"]
    H --> FL["Flash 小模型<br/>普通推理 / 生成"]

### 7.2 杰文斯悖论

## 八、总结

回到开头那个问题：Jev 到底是不是新范式？

我的判断分三层。

**第一层，产品层面。它解决了真问题。** 用 LLM 做分类这件事的荒谬性，即用几千 Token 的自回归生成去做一个 if-else 的判断，确实是过去两年被廉价补贴掩盖掉的。Almeida 说我们本该更早看到这个，是对的。5 到 25 倍的独立实测加速、每千次决策 4 分钱的成本，这些数字站得住。

**第二层，技术层面。它是工程组合，不是架构突破。** RLCD 缺少论文，`confidence` 是算术而非学习产物，架构是逆向出来的而非公布的。把它和 Transformer、Attention、MoE 放在同一个突破级别，目前没有依据。它更像一次极度正确的产品定位，加上扎实的工程取舍。这本身很有价值，但不必把它神话。

**第三层，范式层面。它指出的方向比它本身更重要。** 无论 Jev 这个模型最终成败，Agent 栈需要专用的决策原语，概率校准是自动化的入场券，这两个论断都会被后来者继承。而 Almeida 以 RLHF 共同发明者身份说出的那句"协助已解决，自动化没有"，恐怕是 2026 年 AI 圈最值得咀嚼的一句话。

最后，我认为最有意思的不是技术，而是那个沉默。一个教 ChatGPT 说话的人，转身造了个不会说话的模型，公开说 RLHF 是弯路，而 OpenAI 至今没有回应。**有时候，最有信息量的回应就是不回应。**

至于 Jev 自己，它现在还是个不能解释自己、校准只在群体层面成立、在扑克桌上会自信地把天顺全下、在迷宫里会迷路的模型。

但它的输入价格是每百万 Token 四分二厘，输出免费。

**这个价格，足以让很多人愿意等它长大。**
